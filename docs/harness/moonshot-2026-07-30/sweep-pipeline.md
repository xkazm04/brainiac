## 1. The Demand Ledger — mine what agents ASKED FOR and didn't get, and let the sweep go acquire it

- **Severity**: Critical
- **Category**: demand-side-mining
- **File**: `crates/brainiac-server/src/sweeps.rs:269` (the `execute` kind match — where a `gaps` arm lands) · anchors: `crates/brainiac-server/src/http.rs:369` (`retrieval::search_reranked`), `crates/brainiac-server/src/mcp.rs:827` + `:1084` (`retrieval::search` under `memory_search` / `memory_context`), `crates/brainiac-pipeline/src/divergence.rs:122-152` (the canonical-entity clustering pattern to reuse), `crates/brainiac-pipeline/src/okf_ingest.rs:233` (`harvest`, the acquisition executor), `migrations/0028_library_substrate.sql:149` (`library_usage_events` — the privacy shape to copy)
- **Scenario**: Monday morning a platform lead opens Brainiac and reads: *"Last week your agents asked 312 times about deploy rollback for `checkout-web` and we returned nothing above 0.31. 47 more asks were withheld as contested. The best available evidence lives in three repos nobody has ingested. Queue the harvest?"* One click enqueues an OKF harvest of the named bundles and an interview request to the team that owns the entity. Three weeks later the same sweep reports the gap stopped recurring — the demand curve for "deploy rollback" flattened, and the memories that answered it are now the org's most-served knowledge. Every coding agent in the org has become a sensor: the corpus grows toward what work actually needs, not toward whatever source someone happened to paste in.
- **Root cause**: Brainiac has **no demand-side signal whatsoever**. Verified: there is no query/retrieval log in `migrations/` (the closest thing, `library_usage_events`, counts library artifact fetches, and `document_reads` counts wiki page reads). `retrieval::search` and `search_reranked` are called from three chokepoints and record nothing — not the query, not the top score, not the miss. `memory_feedback` captures verdicts only on memories that *were* returned, so the entire product is blind to the far larger category: the questions it answered badly or not at all. Consequently every sweep in this context mines **supply** — `divergence` clusters existing memories, `library_sweep` mines existing divergences/feedback/contradictions, `okf_ingest` harvests a directory an operator points at. The corpus can only ever get better at what it already knows. The ceiling isn't retrieval quality (five rounds have polished that); it's that nobody knows what's *missing*, so acquisition is guesswork and coverage is unfalsifiable.
- **Impact**: This flips Brainiac from a supply-driven store to a **demand-driven knowledge market**, and it is the single change that makes coverage measurable. Concretely: (a) a ranked, evidence-backed acquisition backlog replaces "which source should we ingest next?" guesswork — the difference between an org ingesting 40 sources and hoping, and ingesting the 6 that answer 80% of unanswered asks; (b) it gives the product its first honest **coverage metric** ("94% of agent asks answered above threshold, up from 61%") which is the number a buyer renews on and which `meridian` can then hold as a regression gate; (c) it makes the withheld-contested count from `mcp.rs` visible as *demand pressure on governance* — "agents needed this 47 times and we refused because you haven't reconciled it" is a far stronger forcing function than a backlog age; (d) at operator scale, aggregate demand shapes across orgs (counts only, no content) reveal the ~50 practices every engineering org asks about, which is the seed corpus for a shipped starter Library — a network effect nobody else in this category has, because nobody else is holding the query stream.
- **Fix sketch**: Order matters; slice 1 is small and immediately valuable.
  1. **Record demand.** New table `retrieval_demand` (org_id, team_id, project_id, query_norm, query_hash, kind_filter, k, hits, top_score, withheld_contested, served_ids uuid[], occurred_at) — deliberately the same privacy invariant as `library_usage_events`: **team, never person**, no user column so it is unrepresentable. Write it from one helper called at the three existing chokepoints (`http.rs:369`, `mcp.rs:827`, `mcp.rs:1084`), fire-and-forget on the admin pool so it can never fail a retrieval. `RetrievalHit` already carries scores, so `top_score` is free.
  2. **The `gaps` sweep.** Register kind `gaps` exactly as 0029 registered `library` (`INSERT INTO sweep_schedules (kind, cadence_secs)`, disabled, weekly) and add an arm to `sweeps::execute`. New `brainiac-pipeline/src/gap_sweep.rs`: bucket the window's demand rows into *unanswered* (`hits = 0` or `top_score` below the eval-derived floor) and *withheld* (`withheld_contested > 0`); cluster the unanswered by embedding the normalized query with `state.embedder` and grouping to the nearest `canonical_entities` row — reusing `divergence.rs`'s canonical-anchor join so "rollback the checkout deploy" and "how do we undo a checkout release" land in one gap. Persist `knowledge_gaps` (org, canonical_id, topic, ask_count, distinct_teams, first_seen, last_seen, best_score, status) with the same *ephemeral-is-wrong* lesson as finding 2: rows accumulate, they don't get wiped.
  3. **Make the sweep act.** For each high-volume gap, name the acquisition move rather than just the gap: the owning team (from the canonical entity's existing memories' `team_id`) gets an ingest request; if a `project_repos` entry carries an OKF bundle path, the sweep proposes `okf_ingest::harvest` on it (already idempotent by content hash, already refuses our own pages) and, once approved, enqueues via `worker::enqueue_source`. Gap-closure is measured by ask recurrence, not by "we ingested something".
  4. **Surface + alert.** Add coverage (answered/asked) to `console::compute_health_core` so it joins the health snapshot trend, and add a `coverage` breach to `alerts::Breach` — "your agents are being told 'I don't know' 200×/week" is precisely what an org wants paged.
  5. **Prove it.** A `meridian` demand profile replays the top recorded gap clusters as fixtures, so "coverage improved" is an eval claim, not a dashboard boast.

## 2. The Convergence Ledger — sweeps that measure whether the org's own norms actually landed, and decide accordingly

- **Severity**: Critical
- **Category**: governance-outcome-loop
- **File**: `crates/brainiac-pipeline/src/divergence.rs:241-269` (the per-run `DELETE FROM practice_divergences` + reinsert — the amnesia) · anchors: `crates/brainiac-pipeline/src/library_sweep.rs:105-131` (`mine_divergences`, which treats a divergence as a one-shot signal), `crates/brainiac-store/src/library/usage.rs:60-80` (`health_signals` — dormancy exists, *effect* does not), `crates/brainiac-server/src/mcp.rs:1996` (`LibraryUsageEvent::Check` — self-reported, no verdict), `crates/brainiac-server/src/alerts.rs:50-121` (`alert_sweep`, threshold-only, one global recipient)
- **Scenario**: A platform lead adopted the standard "all services retry with capped exponential backoff, 30s ceiling" nine weeks ago, mined from a real divergence between payments and platform. Today Brainiac tells her, unprompted: *"That rule has not converged. `payments-api` aligned in week 2. `checkout-web` has recorded three new `howto` memories since adoption that still describe unbounded retries, and its team has never checked the rule. The divergence you thought you closed has been continuously open for 63 days — here is the exact statement pair that still conflicts, and here is a draft escalation to the checkout owner."* Meanwhile another adopted rule is quietly flagged: *"No divergence ever recurred, no team disagrees, nothing has referenced it in 90 days — propose deprecating it? The org outgrew it."* Governance stops being a queue of opinions and becomes an instrument with a measured effect size: every norm the org adopts has a convergence curve attached to it.
- **Root cause**: The sweeps have **no memory of themselves and no notion of outcome**. `divergence::scan_org` wipes the org's entire `practice_divergences` set on every run (`divergence.rs:242`) and re-inserts fresh verdicts — so a divergence has no stable identity, no `first_seen`, no `healed_at`, and no way to distinguish "this drift has poisoned two teams for four months" from "this appeared on Tuesday". Downstream, `library_sweep::mine_divergences` consumes a divergence exactly once and dedups forever via `standard_provenance`, which means the *only* recorded relationship between a drift and a rule is "a candidate was generated" — never "the drift stopped". The Library's health signals measure adoption counts, gate age, and dormancy (`usage.rs`), i.e. *activity*, and the strongest usage signal available, `LibraryUsageEvent::Check`, is an agent self-reporting that it looked at a rule, with no pass/fail verdict. So the product can tell you a rule exists and was fetched, and can never tell you whether practice changed. `alert_sweep` compounds it: it fires on standing thresholds (`REVIEW_SLO_SECS`, currency floor, `cross_contra > 0`) to one global `BRAINIAC_ALERT_WEBHOOK_URL`, with cadence as the debounce — so the recipient gets the same four headlines every six hours with no delta, no owner, and no notion of "this one is getting worse".
- **Impact**: This is the difference between selling a knowledge store and selling **organizational alignment with a measurable ROI**. (a) Every mined standard gains an effect size — "adopted 14 rules, 9 converged practice, 3 had no effect, 2 regressed" is the first sentence in this product that a VP Eng can act on, and it is unavailable to any competitor because it requires holding both the drift detector and the norm registry (Brainiac holds both). (b) It closes the loop the whole `divergence → library_sweep → standards` chain currently leaves dangling: today the pipeline's success metric is *candidates produced*, which rewards volume; with a convergence ledger the metric becomes *drifts healed*, which is the actual product promise. (c) It gives the sweeps something to legitimately **decide** without violating the L2 "generator, never authority" invariant and the `standards_adoption_check` requirement of a named human: the sweep never adopts a norm, but it *can* close a healed divergence, escalate an aging one, downgrade its own confidence class, and file a deprecation proposal for a rule with zero measured effect — decisions about its own artifacts, each reversible and attributed. (d) Alerts finally carry an owner and a delta ("checkout-web, 63 days, worsening") instead of a standing headline, which is the difference between a channel people mute and one they act on.
- **Fix sketch**:
  1. **Give a divergence an identity.** Stop the wipe. Fingerprint each verdict as `(canonical_id, axis, slugify(practice))` and UPSERT in `scan_org`'s transaction instead of `DELETE`+`INSERT`: add `fingerprint`, `first_seen_at`, `last_seen_at`, `run_count`, `status ('open'|'healed')`, `healed_at`. A verdict absent from the current run marks the row `healed` with `healed_at = now()` rather than deleting it — the same "rejection is knowledge" instinct 0029 already encoded, applied to drift. This alone makes "how long has this been true" answerable and makes the existing divergence eval profile a trend rather than a snapshot.
  2. **Link norm to drift.** `library::propose_from_divergence` already writes `standard_provenance` with the divergence id; walk it backwards. New `brainiac-pipeline/src/convergence.rs` computes, per adopted standard with divergence provenance: did the fingerprinted divergence recur after `adopted_at`; per party (team on team-axis rows, project on project-axis rows) whether memories created *after* adoption still support the old approach (reuse the same canonical-entity join `divergence.rs:122` uses, filtered `m.created_at > s.adopted_at`); and whether each *diverging* party specifically has any `library_usage_events` `check`/`apply` for that rule. Persist `standard_outcomes` (standard_id, evaluated_at, verdict `converged|partial|no_effect|regressed`, aligned_parties, holdout_parties jsonb, evidence memory ids).
  3. **New sweep kind `convergence`**, registered disabled/weekly exactly as `library` was, with an arm in `sweeps::execute` that returns an honest detail line ("14 rules: 9 converged, 3 no_effect, 2 regressed; 4 divergences healed, 6 aging"). Deterministic and LLM-free like `library_sweep` — cheap per run, a gate rather than a variance measurement.
  4. **Let it decide, narrowly.** Auto-close healed divergences; auto-file a `proposed` deprecation for adopted rules with `no_effect` plus dormancy (composing with the existing `standards_dormant` signal) — filed as a proposal a named human signs, never a lifecycle flip, so `standards_attribution_check` and the L2 invariant hold; and demote a divergence to a lower confidence class when the adjudicator has re-confirmed it under materially changed positions.
  5. **Alerts grow a subject and a delta.** Extend `alerts::Breach` with `subject` (the standard/divergence), `owner` (the holdout team/project), and `trend` (`new|worsening|persisting|improving`) computed against the prior sweep's ledger rows, and add breach kinds `unhealed_divergence` and `norm_not_landing`. Keep the existing single-webhook decision untouched (per-org channels stay a customer-pulled increment) — the value here is that the payload names *who* and *what changed*, not that it reaches a new destination.
  6. **First slice that proves it:** step 1 alone (UPSERT + `first_seen_at`/`healed_at`), plus a single `console` field "oldest open divergence, N days". `crates/brainiac-pipeline/tests/library_sweep_pg.rs` is the natural home for the ledger test: run `scan_org` twice with the second run's positions converged and assert the row is `healed`, not vanished.
