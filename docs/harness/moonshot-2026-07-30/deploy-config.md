## 1. `brainiac.yaml` — make the instance itself a GitOps artifact, and a fleet falls out of it

- **Severity**: Critical
- **Category**: platform-surface
- **File**: `docker-compose.deploy.yml:62-139` (the ~45-var env block) · `docker-compose.test.yml:62-113` (the same block, restated) · `scripts/first-boot.sh:235-258` (a bash script that rewrites `.env.deploy` in place) · `crates/brainiac-server/src/main.rs:23-120` (the `Command` enum where `apply` belongs, alongside `Reembed` / `OkfHarvest` which are already cross-org operator sweeps) · `crates/brainiac-server/src/provision.rs:41` (`POST /v1/provision`) · `DEPLOY.md:52-68`
- **Scenario**: An org adopts Brainiac by forking a **config repo**, not by editing a `.env`. One committed `brainiac.yaml` declares everything that makes an instance *theirs*: provider + per-stage model routing, orgs/teams/projects with `path_prefix` and visibility tiers, the sources to ingest, token grants with scopes, TTL/re-verification policy, and which eval baseline gates the instance must clear. Install is `git clone acme/brainiac-config && brainiac apply`. Upgrades arrive as PRs against that file — reviewed, diffed, blamed, reverted. `brainiac apply --plan` prints the reconcile diff before touching anything; `brainiac apply --check` in the org's own CI goes red when a human clicked something in the console that the manifest does not describe. Because the instance is now a file, *N* instances are a directory: `envs/{dev,test,prod}.yaml`, or one manifest per customer for whoever runs Brainiac for others — fleet operation with no orchestrator, no control plane, no Kubernetes. And CI can stand up a genuine throwaway instance from a manifest, run `eval` against it, and tear it down.
- **Root cause**: The product sells "GitOps for organizational AI knowledge" while its *own* operational state is imperative and unrecorded. Configuration lives in three places that cannot be reconciled: environment variables (duplicated verbatim across `docker-compose.yml`, `.deploy.yml`, `.test.yml`), a bash script that mutates a secrets file on the host and restarts a container, and hand-clicked console actions writing rows nobody can diff. Nothing about a running Brainiac is reproducible from anything in git. That is why the "5-minute install" is really "edit 15 required vars, then run a hardening script, then configure sources by hand" — and why disaster recovery is `restore.sh` plus institutional memory. The ceiling this caps is not deployment convenience: it is that **a second instance is as expensive as the first**, so self-hosting can never become the distribution engine.
- **Impact**: Time-to-configured-instance drops from "an afternoon of DEPLOY.md" to one command, and the *second* instance costs ~zero. It removes the whole class of divergence bugs this context already documents against itself — `docker-compose.deploy.yml:167-176` admits the console's `NEXT_PUBLIC_SENTRY_DSN` reads are compiled to `undefined` and every `if (dsn)` is dead code, a defect that exists only because config is stringly-typed text pasted between files instead of one validated schema. It makes onboarding reviewable, which is the exact property Brainiac sells for knowledge — the product finally lives its own thesis at the operational layer. And it is the prerequisite for every fleet story: per-customer instances, ephemeral preview instances per PR, and honest cross-instance comparison of eval scores under *declared* configurations.
- **Fix sketch**:
  1. **Schema + planner, read-only.** New `crates/brainiac-config` (serde structs + a validator) and `Command::Apply { manifest, plan, check }` in `main.rs`. Slice one covers only the four resources that already have write paths: orgs, projects (`projects.rs`, `path_prefix` from migration `0039`), sources, and token grants (`POST /v1/tokens`). `--plan` diffs manifest vs DB and prints create/update/no-op per resource, writing nothing. This alone is shippable and immediately useful as drift detection.
  2. **Reconcile.** Make `apply` execute the plan idempotently on the RLS-bypassing owner pool (the same justification `provision.rs:12-19` already writes down for cross-org creation), keyed on stable manifest-declared names so re-running is a no-op. Token grants reuse `first-boot.sh`'s minting logic — the manifest declares *name + scopes*, the secret is emitted to `./secrets/<name>.key` exactly as `--to-file` does today, so no secret ever enters the manifest.
  3. **Absorb the env sprawl.** Add a `providers:` / `routing:` block whose fields map 1:1 onto the existing `BRAINIAC_PROVIDER`, `BRAINIAC_MODEL_{EXTRACT,RESOLVE,CONTRADICT,COMPOSE,DIVERGENCE}`, `BRAINIAC_EMBEDDER` reads, with `${env:QWEN_API_KEY}` / `${file:…}` interpolation for secrets only. The three compose files then pass one `BRAINIAC_MANIFEST` path instead of restating 45 vars, and the duplicated blocks collapse.
  4. **Close the loop in CI.** `apply --check` as a job in `.github/workflows/ci.yml`, and extend `scripts/smoke-test-env.sh` (already a pure-HTTP prover, `:15-30`) with an "instance matches manifest" check so `docker-compose.test.yml` becomes a manifest-seeded ephemeral instance rather than a hand-configured pet.
  5. **Then the fleet.** `envs/*.yaml` + `brainiac apply --manifest envs/prod.yaml` from a GitHub Action = pushbutton multi-instance. Nothing new is needed at this step; it is the payoff of steps 1-4.

## 2. The metered instance — a spend ledger and a hard budget governor that degrades instead of dying

- **Severity**: High
- **Category**: adoption-economics
- **File**: `app-cost.json:6-11` (`"monthly": null … "fill from LightTrack once events flow"`) · `docker-compose.deploy.yml:132-139` (LightTrack deliberately unwired in production, so today *nothing* records production LLM spend) · `crates/brainiac-gateway/src/lighttrack.rs:149` (`"usage": {"input":…, "output":…}` — the numbers exist and are thrown away fire-and-forget) · `crates/brainiac-gateway/src/lib.rs:60-61` (`ChatUsage { input_tokens, output_tokens }`) · `crates/brainiac-gateway/src/resilience.rs:198` (`Resilience::send` — the single chokepoint every provider call passes through) · `migrations/0010_pipeline_run_stats.sql:24-25` (`llm_calls` counted; tokens and dollars not) · `.env.deploy.example:62-63` (the `deterministic` embedder's cost/quality trade is **already measured**: −0.19 NDCG, no API)
- **Scenario**: A stranger evaluating Brainiac points it at their org's repos with their own API key and knows, before starting, that it cannot cost more than the number they wrote down. The manifest carries `budget: { monthly_usd: 40, on_exhaustion: degrade }`. Every provider call debits a per-org ledger with real dollars from real token counts. As the envelope fills, the instance *degrades on purpose and says so*: embeddings fall back to `deterministic` (a −0.19 NDCG hit it can quote, because the eval harness measured it), re-verification sweeps defer, ingest queues rather than drops — and the console shows the posture, the burn rate, and the projected exhaustion date. On the other side of the ledger, the same surface answers "what did this knowledge base cost, and what did it serve": dollars spent vs memories promoted vs agent retrievals delivered vs feedback verdicts, i.e. **cost per trusted answer**. `app-cost.json` stops being a hand-typed file with nulls and becomes generated from the live ledger.
- **Root cause**: Cost is treated as an observability afterthought rather than a controlled resource. Token usage is materialized in `ChatUsage` and immediately serialized into an optional, fire-and-forget HTTP POST to a sink that production explicitly does not enable — so the durable record of what an instance spends is `llm_calls`, an integer, and a JSON file a human edits. There is no price table, no per-org accumulator, and no admission gate: `Resilience::send` will retry a call forever within its circuit-breaker budget with no notion that the org has run out of money. For a **self-hosted** product where the operator brings their own key and an extraction pipeline fans out per chunk, unbounded and unmeasurable spend is the single scariest property of installing it. That fear — not features — is what caps adoption.
- **Impact**: Turns install from an open-ended financial commitment into a bounded one, which is the difference between "I'll try it on a repo" and "I'll ask my company first". Concretely: unbounded → capped at a declared ceiling, with graceful degradation instead of an outage, and `null` → a real number in the cost surface. It also creates a claim no competitor in this space makes — **published cost-per-quality per release**, since CI already computes NDCG (`ci.yml:46-52`) and would now also know the dollars that bought it; a release can ship "NDCG 0.79 at $0.006 per ingested document". And metering is the same code a paid/hosted tier would need, so this is the commercial substrate arriving as a self-hosting safety feature rather than as billing boilerplate.
- **Fix sketch**:
  1. **Persist what already exists.** Migration adding `llm_spend` (org_id, ts, stage, `provider:model`, input_tokens, output_tokens, usd, pipeline_run_id) plus token/usd columns on `pipeline_runs` beside `llm_calls`. Write it where `lighttrack.rs` is already called from, in the same transaction as the pipeline run — the ledger must survive with the work, not alongside it. Slice one stops here: `GET /v1/costs` returns real per-stage, per-model spend for the first time.
  2. **Price table in config.** A `prices:` block in the manifest from finding 1 (`provider:model → usd per 1M in/out`), defaulted for the shipped providers and overridable, because self-hosters negotiate their own rates. Unknown models record tokens with `usd = NULL` rather than guessing — the same honesty posture `app-cost.json`'s `null`s already take.
  3. **The governor.** An admission check in front of `Resilience::send` (it is the one chokepoint, so this is a single wrap): read the rolling-window spend, compare to `budget.monthly_usd`, and on exhaustion apply `on_exhaustion`. `degrade` is cheap to implement precisely because the fallbacks already exist and are already measured — swap the `Embedder` impl to `DeterministicEmbedder` (constructed in `main.rs` today), route stages to the cheapest configured `provider:model`, and pause the `sweeps.rs` re-verification/divergence sweeps. `pause` refuses paid work with a typed error in the existing envelope. Emit an alert through `alerts.rs` at 80% and at exhaustion.
  4. **Generate the cost file.** `brainiac costs --report app-cost.json` replaces hand-editing, and a CI step publishes spend-per-eval-run next to the NDCG artifact `ci.yml:53-62` already uploads.
  5. **The value half.** Join the ledger against promoted-memory counts and `document_reads` (migration `0025`) to render cost-per-trusted-answer in the console. This is the number that makes the ROI argument for adoption, and it is a read-only view over data steps 1-4 already store.
