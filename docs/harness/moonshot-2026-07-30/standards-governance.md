## 1. The ratification record — governance as a legislative process, not a button

- **Severity**: Critical
- **Category**: legitimacy-substrate
- **File**: `crates/brainiac-store/src/library/standards.rs:224` (`adopt_standard`) · `crates/brainiac-server/src/library.rs:773` (`standard_adopt`), `:849` (`standard_reject`), `:886` (`divergence_ratify`) · `migrations/0028_library_substrate.sql:56` (`standard_versions`, write-once in practice) · `crates/brainiac-server/src/mcp.rs:573` (`standards_for` description) · anchors: `console/app/console/modules/standards/triage.ts`, `docs/LIBRARY-PLAN.md` L1/L2/Never-#4
- **Scenario**: A platform engineer opens the `rust` rulebook and sees, on the rule "all fallible service calls carry a bounded retry policy": **mandatory · ratified 3–1 · trial until 2026-09-01 · dissent recorded (Dana: "this hides latency budgets; revisit once the gateway exposes p99") · amended twice (rev 3)**. She disagrees with the current wording, so she does not deprecate the rule and re-propose a near-duplicate — she opens an **amendment**: rev 4, a one-sentence change with a diff against rev 3, argued in a thread where each argument may cite a memory as evidence exactly as provenance does. Because the rule is `mandatory`, the org's ratification policy requires two maintainer signatures, so her amendment sits at the gate until a second maintainer signs; a `recommended` rule in `testing` would need one. Six weeks later, corrective-feedback evidence accumulates against the rule, and the *recorded dissent* is what reopens the docket: Dana's objection is re-surfaced with the new evidence attached, on the rule's page, unprompted. And an agent calling `standards_for("rust")` receives the legitimacy alongside the rule — so it can obey a 4–0 mandatory rule without hesitation and *flag* rather than blindly apply a 3–1 rule still inside its trial window.
- **Root cause**: legitimacy is currently one UUID. `adopt_standard` takes a single `adopted_by`, sets `lifecycle='adopted'` and stamps `adopted_at`; the only enforcement of *anything* about who may decide is the `lib:publish` scope plus the schema's attribution trigger (`standards_attribution_check` — provenance-or-decree). Three consequences cap the ceiling:
  1. **A rule cannot be changed.** `standard_versions` is designed for revisions ("every change to a rule is a numbered revision") but the ONLY `INSERT` into it in the entire workspace is rev 1 inside `insert_standard` (verified by grep across `crates/` + `migrations/`). `versions()` serves a history that can never have more than one row. The de-facto lifecycle is birth (`proposed`) and death (`deprecated`/`rejected`) — the org's *only* way to reword a rule is to retire it and mint a new one, which severs its provenance, its version history, and its usage series. Every "amendment" today is an amnesia event.
  2. **Disagreement is unrepresentable.** There is no table, column, or endpoint for an objection. `reject_standard` records that *someone* said no, in `adopted_by`, and the rule sinks in the tree — but a rule adopted *over* an objection looks byte-identical to one adopted unanimously. A rulebook where dissent is invisible is either unanimous or a lie, and orgs know which.
  3. **All rules are equally cheap to decree.** Making a rule `mandatory` for 200 engineers costs exactly one POST from any token carrying `lib:publish`, the same cost as marking one `experimental`. `users.role` (`member | maintainer`, `migrations/0001_init.sql:34`) exists and is never consulted by this surface.
- **Impact**: this is the difference between a rules *database* and a rulebook an org will actually stake mandatory policy on. Concretely: (a) rule identity survives amendment, so per-rule telemetry (`usage_named`), provenance, and the dormancy signals from LIBRARY-PLAN follow-up 2 accumulate over a rule's *whole life* instead of resetting on every reword — today a 3-year-old rule amended twice has three ids and three empty pulse series, i.e. the instrument that is supposed to be the anti-rot mechanism (L5) is silently reset by the most common maintainer action; (b) `mandatory` becomes expensive in proportion to its blast radius, which is the only known cure for rulebook inflation — the failure mode that kills every standards initiative is 400 mandatory rules nobody can hold in their head; (c) agents get a *confidence-weighted* rulebook rather than a flat list of imperatives, which is what makes 10× more rules survivable rather than 10× more noise; (d) it converts the one product asset nobody else in the category has — governed, evidence-backed org judgment with a named human on every line — into something auditable enough for a regulated org to adopt.
- **Fix sketch**:
  1. **Amendment first (the smallest slice that proves it, and it stands alone).** Add `library::standards::amend_standard(conn, id, &Amendment, author) -> rev` that inserts rev = `max(rev)+1` into `standard_versions`, updates the `standards` row's `statement`/`rationale`/`detail_md`/`enforcement`, and calls the existing `mark_page_for_standard` so the projected page (`crates/brainiac-pipeline/src/standards_page.rs:55` `render_stack`) goes dirty and re-publishes byte-deterministically. Expose `POST /v1/library/standards/{id}/amend` under `SCOPE_LIB_PUBLISH` next to `standard_adopt`. The `standards_page_pg` gate already asserts "the ratified sentence reaches the page byte-identical" — extend it with "an amendment reaches the page and the revision diff shows exactly the amended clause". Note this is *not* the queued triage/editing UI: it is the missing store+HTTP primitive that a triage UI has nothing to call today.
  2. **Amendments go through the gate, not around it.** Model an amendment as a pending revision (`standard_versions.status ∈ draft|ratified|withdrawn`, or a small `standard_amendments` row referencing the target) so the rule keeps serving rev N to agents while rev N+1 is argued. Reuse `triage.ts`'s pure state machine shape so console and backend cannot drift, as LB2 already established.
  3. **Deliberation + dissent.** `standard_arguments (standard_id, rev, position ∈ support|object, author, body, evidence_memory_id?)`, org-scoped RLS + `brainiac_app` grants like every 0028 table. Objections that were live at ratification stay attached to the ratified rev as *minority opinion* — never deleted, the same posture LB3 took with rejections ("rejection is knowledge"). Surface on `StandardDetailResponse` beside `provenance`/`versions`.
  4. **Ratification policy.** `standards_ratification_policy (org_id, stack?, category?, enforcement, signatures_required, signer_role, trial_days?, review_after_days?)` + `standard_signatures (standard_id, rev, signer, at)`. `adopt_standard` becomes "record a signature, and flip to `adopted` only when the policy's threshold is met" — with the invariant enforced where 0028 put its other two: a constraint trigger, so no future code path can adopt under-signed. Default policy for an existing org is `signatures_required = 1`, which makes the change a no-op for everyone already running (the same migration-safety posture as `standards.origin`'s backfill in 0030).
  5. **Serve the legitimacy.** Extend `StandardView` (`library.rs:71`) and the MCP `standards_for` payload with `signatures`, `dissent_count`, `trial_until`, `rev` — and update the tool description so an agent knows what to do with a contested rule. Gate in `library_pg`: a mandatory rule cannot be adopted on one signature under a 2-signature policy; an amendment never reaches an agent before ratification (the exact sibling of the shipped "a PROPOSAL never reaches the page" assertion); dissent survives ratification; amending preserves the rule's id, usage series, and provenance.
  6. **Then the self-relitigation hook**, deliberately last and deliberately thin: when new counter-evidence attaches to a rule, flip a `docket_reopened_at` and let the existing health attention-items surface it. The detection side belongs to the drift instrument — this finding only owns the *reopening*, i.e. what governance does when reality files a brief.

## 2. Rulebook editions — the org's judgment as a signed, effective-dated, pinnable artifact

- **Severity**: High
- **Category**: binding-surface
- **File**: `crates/brainiac-server/src/library.rs:209` (`standards_list` — "whatever is adopted right now") · `crates/brainiac-pipeline/src/standards_page.rs:55` (`render_stack`, deterministic by design) · `crates/brainiac-store/src/library/standards.rs:143` (`list_standards`) · `crates/brainiac-server/src/mcp.rs:686` (`standards_for` dispatch) · anchor: `docs/LIBRARY-PLAN.md` L8 + Never-#3
- **Scenario**: On 2026-08-01 the org publishes **`rust` rulebook edition 7**, effective 2026-09-01: three amendments, one new mandatory rule, two retirements — announced as a diff, with a month of lead time before anything binds. Every agent session pins the edition it read (`standards_for(stack, edition=7)`), and its next session asks "anything new since 7?" and gets a 200-byte "unchanged" or a *changelog of the org's judgment* instead of re-pulling the whole rulebook. When a reviewer looks at a six-month-old file, the rulebook consulted is **the edition in force when that code was written**, not today's — so a rule adopted last Tuesday does not retroactively make 4,000 files non-compliant, and nobody learns to ignore the rulebook because it flooded them once. A maintainer who ships a bad amendment re-issues edition 8 from edition 6's content in one call, and the whole org's agents converge on the rollback within one session each. And "what did we decide this quarter" stops being archaeology across `standards.updated_at` — it is a page: 7 rules changed, 3 retired, 2 promoted from experimental to mandatory.
- **Root cause**: the rulebook has no editions and no clock. `list_standards(stack, Some(Adopted))` is a live query with `ORDER BY stack, category, slug` and no notion of a version *of the corpus* — so (a) there is no name for "the rules as of now", (b) there is no `effective_at`: a rule binds the instant `adopt_standard` commits, meaning the only two available speeds for a policy change are "instant, org-wide, retroactive" or "don't", (c) an agent cannot cache — every session re-fetches every rule and cannot tell a changed rulebook from an unchanged one, so the cost of consulting the rulebook grows linearly with the rulebook and the natural adaptation is to stop consulting it, (d) there is no answer to *what was in force when* — the one question that makes a rule fair to enforce. The projected standards page (L8) versions the *document* through KB revisions, which is a rendering artifact of a stack, not a citable normative edition of the org's rulebook — and notably the render is already fully deterministic, so the hard half of "a snapshot means something" is done.
- **Impact**: this is what turns "informs" into "binds" without violating Never-#3 (no silent enforcement) — because a rule with an effective date and a lead time is *announced*, which is the consent mechanism enforcement was always missing. Quantified: an agent session that consults the rulebook today pays a full corpus fetch every time (100 rules × statement + rationale + verbatim examples is a real slice of a context window); an edition digest turns the steady state into one cheap unchanged-check, so a 10× larger rulebook costs an agent ~nothing more than a 10-rule one — the constraint that decides whether an org can ever hold 500 rules. Strategically it creates the first artifact in the product with a *stable citation* ("edition 7 §errors/bounded-retry"), which is the unit a CI annotation, an audit, or a downstream consumer can name; today nothing in the Library is citable-with-a-date. Editions are also the missing substrate under two things the plan already wants but deferred: enforcement hooks (follow-up #3) become tractable once "which rules, as of when" is answerable, and the sibling context's portable norm packs get a well-defined thing to export — an edition, not a live query result.
- **Fix sketch**:
  1. **Smallest first slice — the digest, and it is independently useful.** `library::editions::corpus_digest(conn, stack)`: a stable hash over the adopted rules' `(slug, rev, statement, enforcement)` tuples, computed in the same ordering `list_standards` already guarantees. Serve it as an ETag on `GET /v1/library/standards` and as a `digest` field on the MCP `standards_for` payload, with `If-None-Match` → 304. Nothing else changes and every agent session gets cheaper immediately. Test in `library_pg`: two calls with no gate activity between them return the same digest and a 304; adopting a rule changes it; a *proposal* does not.
  2. **`standard_editions (id, org_id, stack, seq, digest, issued_by, issued_at, effective_at, notes)` + `standard_edition_rules (edition_id, standard_id, rev)`** — a snapshot of ids+revs, not copies of content, so an edition is a few hundred bytes and cannot drift from the versions it names. `POST /v1/library/editions` under `SCOPE_LIB_PUBLISH` (named human, exactly like every other gate here); `effective_at` defaults to now, may be future-dated.
  3. **Read paths gain an edition lens**: `GET /v1/library/standards?edition=7` and `?as_of=2026-06-01`, resolving through `standard_edition_rules` → `standard_versions` (this is precisely why finding 1's amendment path must exist first — without rev 2 there is nothing for an edition to pin). `standards_for` gains the same two optional params plus the digest. Keep the default behaviour "current effective edition, else live adopted" so no existing caller changes shape.
  4. **`GET /v1/library/editions/{a}/diff/{b}`** — added / retired / amended (with the rev-to-rev statement diff) / enforcement-changed. This one endpoint is the changelog surface, the release-notes page, and the agent's "what's new since I last looked", and it composes with the queued triage UI rather than duplicating it.
  5. **Re-issue = rollback**: `POST /v1/library/editions?from=6` copies edition 6's `(standard_id, rev)` set into a new `seq`, so undoing a bad quarter is one signed call with the reasoning recorded in `notes`.
  6. **Wire the projected page to editions**: `render_stack` takes an optional edition and stamps the edition + effective date in its header — the page a Confluence reader sees then cites something with a date, and its revision diff (already meaningful because the render is deterministic) becomes the org's public rulebook changelog. Gate in `standards_page_pg`, whose existing "a second render is byte-identical" assertion generalizes cleanly to "rendering edition 7 tomorrow is byte-identical to rendering it today, even after edition 8 issues" — the real test that an edition is immutable.
  7. **Scope discipline**: editions stay inside the org (no export, no cross-org surface) — the blast-radius work and the pack format belong to the library-data-layer sibling; this finding builds the substrate it would consume.
