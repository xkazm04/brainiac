## 1. The Sealed Data Plane — make "zero permission leaks" a property of the type system and the catalog, not of 43 hand-written predicates

- **Severity**: Critical
- **Category**: provable-isolation
- **File**: `crates/brainiac-store/src/lib.rs:11` (the claim), `:36` (`pub type Tx`), `:102` (`scoped_tx`), `:129` (`worker_tx`), `:144` (`pub fn pool`), `:71` (`admin_pool`); `migrations/0001_init.sql:40`; 43 `.pool()` call sites across `brainiac-server/src/{http,console,auth,onboard,projects,sweeps}.rs` and `brainiac-pipeline/src/worker.rs`
- **Scenario**: A regulated buyer's security team asks the question that decides the deal — "prove an agent in team A can never retrieve team B's memory, and show me you'd know if that broke." Today the honest answer is a paragraph of design intent. In the end state, Brainiac hands them a **living tenancy proof**: every tenant-bearing table with its enforcing policy, every store function annotated with the scope it is *typed* to accept, every operator-level RLS bypass enumerated with its justification and its last invocation — generated from the live Postgres catalog and the Rust type graph, versioned per release, diffable between releases. And the property behind it is not documentation: a store call issued without a proven scope **does not compile**, and a new tenant table without a policy **fails the build**. Brainiac stops being an org-memory server that takes isolation seriously and becomes the one whose isolation is auditable — which is the only version of this product a bank, a hospital, or a defense contractor can install.
- **Root cause**: The isolation guarantee is architecturally real but **only partially load-bearing, and nothing detects the gap**. Three specific ceilings:
  1. **Scope is untyped.** `scoped_tx` (line 102) and `worker_tx` (line 129) both return the same `Tx<'static>` (line 36). `worker_tx` deliberately sets `app.worker='on'`, which the memories read policy honors as an org-wide read across team tiers. So handing a worker transaction to a store function written for a user request silently widens that user's read to the whole org — and the compiler cannot see it. The doc's own line ("Only pipeline stages use this; end-user requests always go through `scoped_tx`") is a *comment* enforcing a security boundary.
  2. **`pool()` is the real query path for a third of the schema.** Line 144 calls it "raw pool access for non-tenant subsystems (the job queue)". It has 43 call sites, most of them not the queue: `tokens::list(pool, org_id)`, `projects::belongs(pool, org_id, …)`, `onboard::deny(pool, id)`, `sweeps.rs` raw `fetch_all(pool)`. Those sessions are demoted to `brainiac_app`, so policies *would* apply — but no `app.org_id` GUC is set, and the tables mostly have no policy anyway. Tenancy there is whatever the SQL author remembered to type.
  3. **RLS coverage is 26 of 41 tables, and nothing asserts it.** Enumerating `migrations/`: enabled on `memories`, `documents`, `sources`, `promotions`, `standards`, … ; **absent** on `api_tokens`, `identities`, `onboard_requests`, `projects`, `project_repos`, `teams`, `users`, `sweep_schedules`, `memory_embeddings`, `memory_entities`, `entity_links`, `canonical_entity_embeddings`, `embedding_versions`, `orgs`, `queue`. Several of those are unambiguously tenant-bearing (`api_tokens` holds hashed `brk_` credentials per org; `identities`, `projects`, `project_repos`, `sweep_schedules`, `memory_entities` all carry org scope). The next table someone adds inherits the coin flip. This is the constraint being lifted: the substrate offers a *strong default* where the product needs an *inescapable* one.
- **Impact**: Converts the mission's boldest clause ("zero permission leaks") from an aspiration into a checkable artifact, and does it once for all 8 crates. Concretely: closes the ~15-table policy gap and the 43 unscoped call sites; makes the *next* 100 store functions and the next 40 tables safe by construction rather than by review; and removes the single largest objection in enterprise procurement for a product whose whole value proposition is centralizing an organization's most sensitive tacit knowledge. It is also the precondition for the shape of the business that scales — a hosted multi-tenant Brainiac. Today shipping that means betting the company on 43 hand-typed `WHERE org_id = $1` clauses staying correct forever.
- **Fix sketch**: Four slices, smallest first, each independently shippable.
  1. **The invariant that finds the gap (one test, no schema churn).** A `store_pg` test that queries `information_schema.columns` for every table with an `org_id` column, joins `pg_class.relrowsecurity` and `pg_policies`, and asserts each is RLS-enabled with ≥1 policy — with an explicit, *named* allowlist for the deliberate exceptions (`queue`, `orgs`, `embedding_versions`, derived-vector tables reachable only through an already-scoped parent). This is not "migration work as an end in itself" (rejected in prior rounds): it ships zero migrations and produces a fact — the exact list of tenant tables currently defended by nothing but SQL discipline. Everything else is prioritized off its output.
  2. **Type the scope.** Introduce `Scope` marker types in `brainiac-store` — `pub struct Scoped; pub struct Worker; pub struct Operator;` — and `pub struct ScopedTx<'a, S> { tx: Tx<'a>, _s: PhantomData<S> }`. `scoped_tx` returns `ScopedTx<Scoped>`, `worker_tx` returns `ScopedTx<Worker>`. Store functions then *declare* their audience: `memories::retrieve(tx: &mut ScopedTx<Scoped>, …)` cannot accept a worker transaction; pipeline-only readers take `&mut ScopedTx<Worker>`. Migration is mechanical and compiler-driven (a `DerefMut` to `Tx` keeps SQL bodies untouched), and the diff is the audit: every function that needed relaxing is a security decision made explicitly, once.
  3. **Seal `pool()`.** Rename to `operator_pool(reason: OperatorReason) -> &PgPool` returning an `OperatorPool` newtype, where `OperatorReason` is a closed enum (`JobQueue`, `TokenResolution`, `Provisioning`, `ReembedBackfill`) — the same posture `admin_pool` (line 71) already argues for itself in prose. Each construction emits a structured event. Then walk the 43 sites: the true non-tenant ones (queue read/complete/fail in `worker.rs`, `auth.rs` token resolution before a principal exists) declare a reason; the rest (`projects::belongs`, `tokens::list`, `onboard::*`, `sweeps.rs`) move onto `ScopedTx<Scoped>` behind policies added by slice 1's findings.
  4. **The proof endpoint.** `GET /v1/tenancy/proof` — catalog-derived (tables → policies → the GUCs each references) joined with a compile-time inventory of scope-typed store functions and the `OperatorReason` allowlist with last-use timestamps, rendered in the console as a page a customer can export. Deliberately *static/structural*: the sibling context's eval-based leak attestation supplies the adversarial-probe evidence, and the two compose into one document — construction proof plus behavioral proof. Neither substitutes for the other, and shipping the structural half is what makes the behavioral half interpretable.

## 2. Redaction as a sealed boundary — a governed, versioned, org-authored scrubbing policy that turns retained secrets into a security product

- **Severity**: Critical
- **Category**: enforced-boundary
- **File**: `crates/brainiac-core/src/redact.rs:84` (`pub fn redact`), `:33` (11 hardcoded global rules), `:105` (`contains_secret` — defined, documented as "useful for flagging/alerting", **zero callers**); call sites `brainiac-pipeline/src/extract.rs:190,669` and `brainiac-server/src/mcp.rs:2127`; storage path `crates/brainiac-store/src/governance.rs:23,56` into `migrations/0001_init.sql:46` (`sources.raw_text`)
- **Scenario**: A platform team installs Brainiac and, three months later, their CISO is the loudest internal advocate — because Brainiac is the only system that sees what engineers actually paste into agent sessions. It reports: *"Q3: 47 credentials entered agent transcripts. 31 were AWS keys from the `payments` repo's runbook flow. Two are still live — here they are, redacted, with the source, the author, and the timestamp. Your rotation policy has a hole at the runbook step."* Meanwhile the org has authored its own scrubbing patterns — employee IDs, internal hostname formats, customer account numbers, the one client whose name is contractually unmentionable — proposed and adopted through the same review queue that governs its memories, versioned, with the corpus rescanned retroactively when the policy improves. And the reason a maintainer trusts all of it: **no crate in the workspace can write or serve unscrubbed text, because the type won't allow it.**
- **Root cause**: Redaction is a `pub fn` that three call sites remembered to call. That is the whole enforcement mechanism, and it caps three separate ceilings at once:
  1. **It is opt-in at the wrong layer.** `sources.raw_text` stores the transcript **verbatim** — the insert at `governance.rs:23`/`:56` scrubs nothing. Redaction happens on *derived output* (`extract.rs:190,669`) and on *one egress path* (`mcp.rs:2127`, the `memory_provenance` excerpt). So the credential is retained at rest indefinitely, and every future reader of `raw_text` — a docs composer, a console source viewer, an export endpoint, next quarter's MCP tool — is one forgotten `redact()` call from the exact breach the module header was written to close. The header's own history proves the failure mode: it documents two bugs (a promised-but-missing bearer rule, `\btoken\b` unable to match inside `access_token`) that shipped *because* correctness lived in a helper nobody could verify was reached.
  2. **The policy is global, static, and org-blind.** Eleven regexes covering public-provider key shapes. An org's actual sensitive shapes — its ID formats, its hostnames, its people — are unexpressible. And when the pattern set improves (as it twice has), the corpus already stored under the old set is never revisited.
  3. **Detection is thrown away.** `contains_secret` exists, is documented for exactly this, and is called by nothing. Every credential Brainiac finds is silently masked and forgotten — the highest-signal security telemetry in the building, discarded at the moment of capture.
- **Impact**: Flips the substrate's biggest liability into its most defensible surface. Today "we store your raw transcripts, and scrubbing is applied where we remembered" is a finding in any serious security review. After: unscrubbed text is **unrepresentable** in the store — a guarantee that holds for all 8 crates and every crate not yet written, at zero ongoing review cost. Then the same machinery yields a capability no standalone secret scanner can match: GitHub/GitLab scanners see committed code, Brainiac sees the *session* — the paste that never reached a commit, which is where credentials actually leak. That is a second buying center (security, not just platform engineering) for infrastructure the product already operates, and it makes the transcript ingest pipeline — currently a cost and a risk — the reason the org wants Brainiac installed.
- **Fix sketch**: Three slices; slice 1 alone is the finding.
  1. **The sealed boundary.** In `brainiac-core`, add `pub struct Sanitized(String)` whose only constructor is `Sanitized::scrub(&str) -> (Sanitized, Vec<Detection>)` — `redact` becomes private behind it, and the detections fall out of the same pass instead of needing a second `contains_secret` scan. Change `governance.rs::insert_source` / the idempotent variant (`:23`, `:56`) and the memory-content writer to take `Sanitized` instead of `&str`. The compiler then walks every producer for you; `raw_text` becomes scrubbed-at-rest, and the `mcp.rs:2127` read-path scrub becomes belt-and-braces rather than the only line of defense. Keep one narrowly-typed `Sanitized::trusted_verbatim(reason)` escape for genuinely pre-scrubbed internal encodings (`encode_add_source` in `http.rs:598`), so the exceptions are enumerable.
  2. **Versioned, org-authored policy.** A `redaction_policies` table modeled directly on the `embedding_versions` pattern that already exists here (versioned artifact + activation + a cross-org derived-data backfill — `admin_pool` at `store/src/lib.rs:71` documents precisely this precedent for `reembed`). Org-authored patterns are proposed and adopted through the existing promotion/standards review loop, so a new pattern is a governed decision with provenance, not a config edit. Stamp `redaction_version` on `sources` and `memories`; a `rescan` job mirrors `reembed`'s shape — re-scrub content already stored when a better policy activates. Patterns validated on submission (compile + a bounded-runtime check) so an org cannot ReDoS its own ingest.
  3. **The hygiene surface.** Persist `Detection` rows (kind, source_id, actor, occurred_at — never the secret) and expose leak counts, top offending sources/flows, and trend as an org report. Follow `health.rs`'s own explicit posture (`:24-38`): ship these as **signals with attention items, deliberately outside the four-pillar composite**, because redefining a number orgs trend week-over-week would break every comparison — the same argument the Library signals already won. Add MCP/REST surfacing so an agent can be told "this source is quarantined pending rotation" rather than silently served a scrubbed body.
