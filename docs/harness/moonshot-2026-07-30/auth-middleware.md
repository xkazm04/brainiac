## 1. Every memory learns whose it is — the actor trust graph that makes retrieval self-calibrating

- **Severity**: Critical
- **Category**: actor-trust-graph
- **File**: `crates/brainiac-pipeline/src/extract.rs:644-655` (the one and only provenance writer) · anchors: `crates/brainiac-server/src/auth.rs:114-133` (`AuthContext`), `migrations/0001_init.sql:52-61` (`provenance.actor_kind` / `actor_id`, unused since day one), `crates/brainiac-store/src/retrieval.rs:360-396` (`feedback::trust_for` → `blended_score`), `crates/brainiac-server/src/mcp.rs:2138-2156` (`memory_provenance` output), `migrations/0004_memory_feedback.sql`
- **Scenario**: Today a maintainer asks the obvious question — *"who wrote this, and do they usually get it right?"* — and the system cannot answer either half. Every provenance row in the corpus says `actor_kind = pipeline`, `actor_id = "extract-worker"`, because that string is a literal at `extract.rs:648-649`. The only human-ish handle is `sources.created_by`, which is the *token's owner user*, so Claude Code running in repo A, a CI importer, a colleague's manual note, and a Cursor session on a shared org-wide key are one indistinguishable contributor. `memory_provenance` faithfully reports three constants.
  The end state: every provenance row names a **verifiable actor** — a human, or a *named agent identity* (device-key name + MCP `clientInfo` + the `model_ref` the provider actually reported). Once actors exist, the outcome signals the product already collects — `memory_feedback` verdicts (0004), contradiction resolutions, dispute outcomes, TTL re-verification results, practice divergences (0016/0037) — roll up per actor into a reliability record. Retrieval then blends an actor prior alongside the per-memory feedback nudge it already blends. The review queue auto-promotes from actors with a proven track record and hard-gates unproven ones. The console gains a contributor board: which agent, which model, which human writes knowledge that *survives contact with reality*. A maintainer can say "the 2026-06 extractor model degraded on `pitfall` kinds" and see it, instead of disputing forty memories one at a time.
- **Root cause**: `Principal` (`brainiac-core/src/types.rs`) and `AuthContext` (`auth.rs:114-124`) collapse "who" into `(org_id, user_id, team_ids, project_id)`. There is no identity *below* the user — an `api_tokens` row has a `name` (0003) but that name never propagates past `resolve_bearer` (`auth.rs:154-188`), which throws away everything except the principal, the scope list, and the project. So the schema slot built for this in migration 0001 (`actor_kind text -- human | agent | pipeline`, `actor_id text`) has been dead for the whole life of the project, and every downstream trust signal is stranded at the row level. Trust can only ever be a property of a memory, never of a producer.
- **Impact**: This converts corpus reliability from a per-row property that costs one human decision per row into a **learned property of producers**, which is the only version that scales. Concretely: at ~30 outcome signals per actor you can rank actors; one bad extraction model or one over-eager agent gets globally discounted from a handful of verdicts instead of needing a dispute per memory — a governance loop that gets *cheaper* as the corpus grows rather than linearly more expensive, which is the difference between a queue a maintainer drains and one they abandon. It is also the first honest answer to the objection every buyer of this product raises: *"why would I trust memory an agent wrote?"* — "because the system measures which agents hold up, and ranks accordingly." The stated mission is "retrieval quality an agent can trust"; today trust has no subject to attach to.
- **Fix sketch**:
  1. **Slice 1 — make `actor_kind`/`actor_id` tell the truth (the whole proof, additive only).** `tokens::ResolvedToken` (`brainiac-store/src/tokens.rs:13`) gains `id` + `name`; `AuthContext` gains `token: Option<(Uuid, String)>`. Add `sources.created_by_token uuid` and pass it through the two ingest call sites that already pass `Some(principal.user_id)` — `http.rs:602-613` / `http.rs:656-668` and `mcp.rs:1277-1290`. Then `extract.rs:644` stops hardcoding: derive `ActorKind::Agent` + `actor_ref = api_tokens.name` for a device-key source, `ActorKind::Human` for a console/env principal, `Pipeline` only for machine-only imports. `memory_provenance` (`mcp.rs:2140-2145`) becomes truthful with zero code change — that is the cheap, visible win.
  2. **Slice 2 — the outcome ledger.** An `actor_outcomes` view joining `memory_feedback`, contradictions and re-verify results onto `provenance.actor_id`; `GET /v1/actors` + a console contributor panel. Read-only, no ranking risk.
  3. **Slice 3 — feed retrieval.** `feedback::trust_for` (`retrieval.rs:366`) returns an `ActorSignal` beside `FeedbackSignal`; `blended_score` (`brainiac-core::scoring`) takes it as a second tiebreak-scale nudge. Gate it behind a **new `meridian` axis (`actor-prior`)** so the weight is proven on golden fixtures, never guessed — the repo's own red-first rule.
  4. **Slice 4 — governance.** `brainiac-pipeline/src/policy.rs` reads actor reliability for auto-promotion thresholds. Only after slice 3's eval says the signal is real.
  Capture MCP `clientInfo` at `initialize` and persist it on the token's session so "Claude Code 2.x" and "a shell script" are different actors on the same key — that is what makes per-*agent* reputation distinct from per-token.

## 2. Tokens that hand down narrower tokens — delegation chains for agent fleets, and the cross-org knowledge network they unlock

- **Severity**: High
- **Category**: delegated-capability-network
- **File**: `crates/brainiac-server/src/auth.rs:154-188` (`resolve_bearer`) · anchors: `auth.rs:97-133` (`SCOPES`, `AuthContext::allows`), `crates/brainiac-server/src/http.rs:1396-1460` (`POST /v1/tokens`, admin-gated minting), `migrations/0040_project_isolation.sql`, `migrations/0020_kb_publishing.sql` + `0041_okf_publish_target.sql` (the one-way export surface), `docs/VISIBILITY-TIERS.md:§2.5` (the red-first eval gate this must pass)
- **Scenario**: An orchestrator agent picks up a task and fans out six sub-agents. Today its only option is to hand each of them **its own bearer token**: full scope, no expiry, no task bound, no project narrowing, and nothing in the record separating their writes. Least privilege inside a fleet is not expressible, and every new credential costs an admin round trip (`POST /v1/tokens` requires `admin`).
  End state: a credential is a **root `brk_` secret plus a chain of caveats the holder appends itself, offline** — scope subset, project subset, TTL, task ref, write budget — where the server can only ever *narrow* what the root resolved to. A researcher sub-agent gets `read`, ten minutes, one project, and the audit trail answers "which sub-agent of which task wrote this memory".
  Then the second, larger door opens. Because the credential is self-describing and verifiable, one org can issue a **guest** credential to another org's agent: *"this contractor's agent may read our `payments` project standards for the length of this engagement."* The publish surface today is a one-way export (KB publishing, OKF target). With delegation it becomes a **two-way trust network**: an org subscribes to a vendor's or a partner's standards, every imported memory carries its origin org + engagement + delegation path, and the whole relationship is revoked by revoking one root. A consultancy running twenty client orgs stops being twenty silos and becomes a hub — the knowledge it earns on one engagement is citable, with attribution and revocability, on the next.
- **Root cause**: authority here **is a database row**. `resolve_bearer` does `tokens::resolve(pool, sha256(bearer))` and returns a fixed `Principal` + a fixed `Vec<String>` of scopes; `AuthContext::allows` (`auth.rs:127-133`) is a flat any-of match with an `admin` wildcard. Three ceilings follow directly: (a) a credential can only be *minted* by an admin, never *derived* by its holder, so the number of principals the system can serve is the number of rows a human will hand-create; (b) a credential has no time, task, or budget dimension at all — the only lifecycle verb is `revoke`; (c) `Principal.org_id` is single-valued and every RLS GUC keys off it, so nothing can ever act across an org boundary, which forecloses the only network effect this product has available (memories are org-private by construction).
- **Impact**: Two multipliers on the same mechanism. **Fleets**: one root key fans out to an unbounded number of least-privilege sub-principals with *zero* server round trips — a 10-agent swarm goes from "10 copies of a full-authority key" to 10 credentials each narrower than their parent, which is the difference between an audit story you can sell and one you cannot. **Federation**: cross-org knowledge exchange is the only compounding surface Brainiac has, and attenuated, revocable, attributed delegation is the only mechanism that makes it a feature instead of a leak. It also inverts the sales motion — a vendor publishing standards to its customers' Brainiacs makes every customer's install more valuable, and every install a distribution channel for the next.
- **Fix sketch**:
  1. **Slice 1 — the attenuation grammar (no migration, and it is the whole proof).** Wire format `brk_<root>.<b64(caveat)>.<hmac>`, where each link's HMAC key is the *previous* link's digest — so appending a caveat is pure client-side arithmetic, while forging a *wider* credential needs the root secret. In `resolve_bearer`, split on `.`, resolve the root through `tokens::resolve` exactly as today, then fold each caveat as an **intersection** over the resolved `AuthContext`: `scopes` → set intersection with `SCOPES`, `project_id` → may only be set or kept, plus new `expires_at` and `task_ref`. Add `AuthContext::attenuate(&Caveat)` beside the existing `allows` tests (`auth.rs:190-233`) with the property test that makes this shippable: **no caveat sequence can ever widen the context**. Every fold narrows, so any bug is fail-closed — the same discipline `SCOPES`' own comment was written in blood about.
  2. **Slice 2 — make the chain visible.** Thread `task_ref` + the chain digest into provenance alongside Finding 1's `actor_ref`, so "which sub-agent, under which task, delegated by whom" is answerable on `memory_provenance` and in the console audit module.
  3. **Slice 3 — the guest arm (the federation half).** A `guest_grants` table (host org, guest identity from `identities` (0022), project subset, expiry, `granted_by` a named human) and one additional arm in `resolve_bearer`. Critically: a guest resolves to a **host-org `Principal` capped to the granted projects**, leaning on `0040_project_isolation` — so no RLS policy file is amended and the contractor-tier design's sequencing warning is respected. Per `VISIBILITY-TIERS.md §2.5`, the leak suite gains `guest-*` fixture askers (pre-grant project invisible, granted project visible, team/private rows invisible, team pages not found) and they must be **red before the resolver arm is written**.
  4. **Slice 4 — surface + revocation.** `GET /v1/delegations` and a console view; revoking a root invalidates every descendant for free, because the chain is keyed off it.
  Deliberately **not** token-lifecycle rework (on the rejected list): the `brk_` rows' minting, listing, and revocation are untouched. This adds a holder-side attenuation grammar and a guest arm *on top of* the existing resolver.
